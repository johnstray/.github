# Contributing Guidelines

Hi there! I'm thrilled that you'd like to contribute to this project, your help is essential for keeping it great. Everyone is welcome to make suggestions on how this project can be improved. You can do this by either submitting an issue to report a bug or discuss a feature, or a pull-request to fix a bug or add a feature.

Before contributing, please take a moment to read these guidelines. Individual repositories may also contain additional contribution or development documentation that should also be followed.

Contributions to projects using this guide are released under the license applicable to the relevant repository.

## Code of Conduct

Please read and follow the project's [Code of Conduct](https://github.com/johnstray/.github/blob/main/CODE_OF_CONDUCT.md).

By participating in a project, you agree to follow its terms.

## Reporting Bugs and Other Issues

Before opening an issue:

- Search the existing issues to see whether the problem has already been reported.
- Check the project's documentation and troubleshooting information where available.
- Make sure you are using a supported version of the project.

When opening an issue, provide as much relevant information as possible, including:

- A clear and descriptive title.
- A description of the problem.
- Steps to reproduce the issue where applicable.
- Expected behaviour.
- Actual behaviour.
- Relevant error messages, logs, or stack traces.
- Information about your environment or configuration when relevant.

Please remove passwords, API keys, tokens, and other sensitive information before submitting logs or configuration files.

## Suggesting Features and Improvements

Feature requests and improvements are welcome.

For significant changes, please open an issue before starting implementation. This provides an opportunity to discuss the proposed change and determine whether it fits the project's goals and direction.

When suggesting a feature or improvement, explain:

- What problem it would solve.
- Why the change would be useful.
- How you expect it to work, where practical.
- Any relevant alternatives or limitations.

Small improvements and straightforward fixes may not require a separate discussion when the intended change is clear.

## Pull Requests

Pull requests are the preferred way to submit code changes.

Before opening a pull request:

1. Check the existing issues and documentation.
2. Create a branch for your changes.
3. Keep your changes focused and limited to the issue or improvement being addressed.
4. Test your changes appropriately.
5. Update documentation when the behaviour or usage of the project changes.
6. Make sure you have not included secrets, credentials, generated files, or unrelated changes.

When opening a pull request:

- Clearly describe the problem being addressed.
- Explain the changes made.
- Reference the related issue where applicable.
- Include relevant testing information.
- Mention any known limitations or follow-up work.

Unless a repository specifies otherwise, pull requests should target the repository's default development branch.

## Commit Guidelines

Please keep commits focused and meaningful.

Good commits generally:

- Address one logical change.
- Use a clear and descriptive commit message.
- Avoid unrelated formatting or refactoring.
- Do not include generated files unless they are intentionally part of the project.

A useful commit message describes what the commit does rather than simply stating that something changed.

For example:

```text
Add configuration validation
```

is generally more useful than:

```text
Updated files
```

## Code Quality

Contributed code should follow the existing style and conventions of the project.

In general:

- Prefer readable and maintainable code over clever or unnecessarily complex solutions.
- Follow the language and framework conventions already used by the project.
- Avoid introducing unnecessary dependencies or abstractions.
- Keep changes consistent with the existing architecture.
- Add comments where they improve understanding, but avoid comments that merely restate the code.
- Update documentation when necessary.

Individual repositories may define additional coding standards or tooling requirements.

## Testing

Changes should be tested before submitting a pull request.

The appropriate level of testing depends on the project and the change. This may include:

- Unit or automated tests.
- Integration tests.
- Manual testing.
- Configuration validation.
- End-to-end testing.

Where a project provides automated tests, please run the relevant test suite before submitting your pull request.

If automated testing is not available, describe the manual testing you performed in the pull request.

## Documentation

Documentation is an important part of a contribution.

Please update relevant documentation when your change affects:

- Installation.
- Configuration.
- User-facing behaviour.
- Command-line usage.
- APIs or interfaces.
- Deployment or operational procedures.

Documentation changes are welcome even when they are not accompanied by code changes.

## Review Process

Pull requests may be reviewed for:

- Correctness.
- Compatibility with the project's goals and existing architecture.
- Code quality and maintainability.
- Testing and regression risk.
- Documentation.
- Security considerations.

Reviewers may request changes before a pull request is accepted.

Contributors are encouraged to participate in the review discussion and provide additional information where requested.

## Licensing

By contributing to a repository, you agree that your contribution may be distributed under the license applicable to that repository.

Please ensure that you have the right to submit the code, documentation, images, or other material included in your contribution.

## Security Issues

Please do not report security vulnerabilities through public GitHub issues.

Instead, follow the security reporting instructions provided by the repository, where available.

If no specific security policy is provided, contact the repository maintainer privately before disclosing a suspected vulnerability publicly.
